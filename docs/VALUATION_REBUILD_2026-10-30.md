현재 초기 가격에 사용할 수 있는 이전 시즌 점수는 8,432개, 해당 경기 수는 278개다. 선수·포지션별 유효 출전 수의 중앙값은 3개, 최대 7개다. 나머지 1,473경기는 해당 원천만으로 유효 점수를 만들지 못했다. 초기 가격 대상 2,901명 중 1,527명은 본인의 유효 과거 기록을 사용하고, 1,374명은 보고서의 신규/기록 부족 선수 규칙에 따라 포지션 평균으로 보정한다. 예시의 과거 출전 4~5개는 최근 5경기만 사용하도록 제한한 결과가 아니다.

**추가 점검으로 확인한 원인:** 원천 1,751개를 모두 다시 검사했으며 빈 선수 통계, 미확정 라인업, 사건 목록 자체의 누락은 각각 0개였다. 통계 행은 총 74,282개였다. 그러나 5개 리그의 비계산 경기 표본을 확인하니, 라인업에 포지션은 있어도 선수 `id`가 `null`이었다. 통계의 `player_id`와 연결할 수 없어서 코드가 `MATCH_POSITION_REQUIRED`로 보류한 것이다. 현재 API로 리그당 한 경기씩 다시 조회한 5건도 동일했다. 이름만으로 과거 선수 ID를 추정해 원천을 덮어쓰지 않았다.

즉, 문제는 과거 통계 전체를 안 가져온 것이 아니라 **과거 라인업의 선수 식별자 결손**이다. 1,473경기의 개별 원인이 모두 같다고 단정하지는 않지만, 전 리그의 과거 표본에서 동일한 차단 원인을 확인했다. 공급자에서 ID 연결을 보완하거나, 같은 경기·선수를 신뢰할 수 있게 연결하는 별도 자료를 확보해야 해당 기록까지 반영할 수 있다. 현재 초기 가격을 '직전 시즌 전체 출전을 완전 반영한 가격'이라고 표현해서는 안 된다.

## 과거 소속과 미출전의 한계

과거 경기의 확정 벤치 명단·결장자 명단·그 시점 이전에 확보된 선수단 관측으로 소속이 입증되는 경우만 하락을 적용한다. 현재 스쿼드를 과거 경기로 소급 복사해 모든 선수를 결장 처리하지 않는다.

새 소속 관측은 스쿼드가 바뀌면 작은 ID 목록을 추가하고, 동일한 명단을 7일 안에 다시 확인하면 마지막 확인 시각만 갱신한다. 7일 넘게 확인이 끊겼다면 명단이 같아도 새 관측으로 기록해 확인하지 않은 기간을 소급해서 연결하지 않는다. 원천이 같아서 DB 쓰기를 건너뛰는 경우에도 실제 재확인 시각은 남도록 트리거 순서를 수정했다. 과거에 벤치/결장자 목록에도 없고 당시 소속 관측도 없는 선수의 미출전 여부는 데이터만으로 확정할 수 없다. 이 경우 임의의 −1.5%를 만들지 않는다.

## 운영 적용 순서

1. 명시적인 운영 변경 승인 확인.
2. migration 적용. 이 단계에서 백업·기준 자료·호환 배포 확인 없이 새 가격을 활성화하지 않는다.
3. 최신 팀/스쿼드/전체 일정 대조와 일반 수집 경로를 통한 누락·소속 보완.
4. 기존 점수·가격·초기가격·평가/랭킹 이력을 비공개 압축 백업하고 복구 바이트 검증.
5. 이전 시즌 원천 1,757경기를 끝까지 확보한 뒤 승강 관련 6개를 제외하고, 정규 종료 경기 1,751개로 네 포지션 모집단을 확정한다. 준비 중인 일부 경기만으로 가격을 임의 확정하지 않는다.
6. 호환 코드 배포 확인 후 초기 가격을 새 기준으로 설정하고 자동 계산 큐로 경기 결과를 재생.
7. 보류 선수/누락/무결성 검사, 거래·잔액·취득 원가 보존 확인, 자산 평가 이력과 랭킹 갱신.

과거 자료 수집은 기존 공유 API 예산과 라이브 경기 여유를 지킨다. 호출 한도나 공급자 자료 불일치가 남으면 중단 지점에서 재개하며, 완료되지 않은 작업을 완료로 표시하지 않는다.

## 검증

241개 단위 테스트, PGlite의 전체 migration/SQL 통합 검사, 타입 검사와 프로덕션 빌드가 통과했다. 실제 PostgreSQL 17의 SQL/권한 검사와 PC·모바일 브라우저 회귀 검사까지 CI 전체가 통과했다(최종 코드 검증: 실행 41036559502). redirect/polling 화면은 networkidle 대신 화면 준비 상태를 기다린다.

대량 초기 가격 활성화에서는 큰 기준 JSON을 선수마다 압축 해제하던 작업을 한 번으로 줄이고, 재계산 대기열 등록을 일괄 처리했다. 동일한 2,901명 초기 가격 산출 SELECT는 운영 DB에서 약 10.95초에서 0.24초로 줄었다. 가격 수식의 계수나 계산 결과를 바꾼 최적화는 아니다.
